# TraceFlow UI Surface Inventory

## Purpose

Este documento é a fonte canônica de rastreabilidade das superfícies visuais do frontend do
TRACEFLOW. O inventário acompanha páginas, estados e fluxos auxiliares que precisam ser considerados
em conjunto durante redesign, implementação e homologação.

Uma área visual não é considerada completamente revisada apenas porque sua rota principal foi
avaliada. Dialogs, confirmações, drawers, estados vazios, loading, erros, sucessos, restrições e
callbacks diretamente associados fazem parte do mesmo escopo.

Atualize este inventário quando uma surface for criada ou removida, quando um redesign alterar seu
estado visual ou quando uma homologação modificar o nível de evidência. Alterações internas de CSS
ou de componentes que não criem nem mudem uma surface não exigem uma nova linha.

Fontes principais desta auditoria:

- rotas em [`AppRoutes.jsx`](../../frontend/src/app/routes/AppRoutes.jsx);
- owners em `frontend/src/app`, `frontend/src/pages`, `frontend/src/features` e
  `frontend/src/shared`;
- renderizações condicionais e estados inline nos componentes;
- testes em `frontend/test`;
- [Design System](DESIGN_SYSTEM.md),
  [Visual Validation Log](validation/VISUAL_VALIDATION_LOG.md),
  [contratos da API](../api/API_CONTRACTS.md),
  [matriz de autorização](../security/AUTHORIZATION_MATRIX.md) e
  [matriz RF](../traceability/RF_TECHNICAL_MATRIX.md).

## Status taxonomy

| Visual Status    | Uso                                                                                                                          |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `C2 COMPLETE`    | A surface segue o TraceFlow Hybrid C2 em Light, Dark e composição responsiva, com evidência suficiente para a classificação. |
| `LEGACY`         | A surface ainda utiliza predominantemente a linguagem visual anterior.                                                       |
| `HYBRID`         | A surface combina shell, tokens ou primitives C2 com conteúdo ainda legado.                                                  |
| `NOT REVIEWED`   | A surface foi identificada, mas faltam evidências para classificar sua linguagem visual.                                     |
| `NOT APPLICABLE` | O item rastreado não possui apresentação visual própria.                                                                     |

Prioridade visual:

- `P0`: surface quebrada, ilegível ou inacessível para uso;
- `P1`: próxima fase de redesign;
- `P2`: dívida visual relevante, sem bloqueio imediato;
- `P3`: baixo impacto;
- `—`: baseline aprovada ou primitive transversal sem redesign pendente.

## Validation taxonomy

| Validation Status         | Uso                                                                                  |
| ------------------------- | ------------------------------------------------------------------------------------ |
| `VISUALLY APPROVED`       | Homologação renderizada concluída no escopo registrado no log versionado.            |
| `TECHNICALLY VERIFIED`    | Código e testes sustentam a evidência declarada, sem equivaler a homologação visual. |
| `STRUCTURALLY IDENTIFIED` | Rota, owner, trigger e estados foram localizados por auditoria estrutural.           |
| `ENVIRONMENT BLOCKED`     | A validação pretendida não pôde ser executada por limitação objetiva do ambiente.    |
| `NOT VALIDATED`           | A surface existe, mas ainda não possui validação registrada.                         |

As colunas Light, Dark, Responsive e Accessibility registram evidência separadamente. “Tokenizado”
não significa “homologado”, e teste estrutural não substitui inspeção renderizada.
`TECHNICALLY VERIFIED` limita-se ao comportamento explicitado nessas colunas e nas notas; não prova
todos os estados de uma surface. `ENVIRONMENT BLOCKED` não é aprovação nem falha. Uma mudança
material posterior preserva a entrada histórica no log, mas exige reconsiderar o status atual até a
revalidação.

   canvas possuem compatibilidade Dark; o canvas preserva sua light island categórica. O redesign
   continua adiado.
3. **Repository:** filtros, summary e tabela possuem compatibilidade Dark, mas ainda pertencem à
   linguagem anterior.
4. **Project Audit:** a rota continua legada e sem entrada na navegação; Settings é C2 e possui
   validação granular própria, sem promover Project Audit por associação.

A compatibilidade de tema registrada não altera a classificação LEGACY/HYBRID nem antecipa o
respectivo UX scope de redesign.

## UX Scope Planning

Os identificadores `UX-*` organizam somente a evolução visual e sua validação. Eles não substituem
Sprints, RFs, cards do roadmap nem a linhagem técnica/histórica E0-E15 preservada em migrations,
scripts, ADRs, testes e documentos de refatoração.

- Design System e tokens semânticos;
- shell autenticado, sidebar, drawer, quick projects e primitives transversais;
- preferências Sistema/Claro/Escuro e resolução do tema;
- bypass block, landmarks e comportamento responsivo do shell.

### UX-PROJECTS — Projects / Overview / Edit / Members

- Project Overview e sincronização GitHub contextual;
- Edit Project;
- Members, convites, Access Code e confirmações relacionadas.

### UX-AUTH — Auth + Auxiliary Flows

As 15 surfaces de Auth e Account Lifecycle usam C2 Focused. A evidência renderizada histórica está
no log; o status corrente continua granular no inventário. Não criar página visual própria para
`ANONYMIZED`: o estado vigente não autentica. Callbacks iniciados dentro de Settings permanecem no
escopo UX-SETTINGS; as callbacks públicas de mudança de e-mail e reativação pertencem a UX-AUTH.

## Audit Notes

- Todas as rotas declaradas em `AppRoutes.jsx` foram mapeadas, inclusive redirect de `/`, nested
  routes de Settings e wildcard 404.
- A auditoria cruzou arquivos, imports, JSX condicional e testes; não se limitou ao route table.
- `OWNER`, `MANAGER`, `MEMBER` e `VIEWER` são os únicos papéis de projeto usados. `OWNER` não é
  administrador do sistema.
- Usuário autenticado sem membership pode acessar a plataforma e `/projects`; recursos de projeto
  sem membership permanecem inacessíveis.
- GitHub OAuth foi catalogado como autenticação/identidade. GitHub App/Installation foi catalogada
  como integração de repositórios e artefatos.
- Surfaces de features planejadas, sem owner/runtime atual, não foram incluídas nos totais. O item
  `ACCOUNT-AUDIT-UNIMPLEMENTED` é mantido fora dos totais apenas para registrar a lacuna entre o
  endpoint documentado e o frontend atual.
- O log preserva a homologação histórica, enquanto este inventário registra o estado após mudanças
  materiais. Protótipos locais não promovem uma surface nem substituem evidência versionada.
