# TraceFlow UI Surface Inventory

## Purpose

Este documento é a fonte canônica de rastreabilidade das superfícies visuais do frontend do
TRACEFLOW. O inventário acompanha páginas, estados e fluxos auxiliares que precisam ser considerados
em conjunto durante redesign, implementação e homologação.

Uma área visual não é considerada completamente revisada apenas porque sua rota principal foi
avaliada. Dialogs, confirmações, drawers, estados vazios, loading, erros, sucessos, restrições e
callbacks diretamente associados fazem parte do mesmo escopo.

Atualize este inventário quando uma surface for criada ou removida, quando um redesign alterar seu
estado visual ou quando uma homologação modificar o nível de evidência. Alterações internas de CSS
ou de componentes que não criem nem mudem uma surface não exigem uma nova linha.

Fontes principais desta auditoria:

- rotas em [`AppRoutes.jsx`](../../frontend/src/app/routes/AppRoutes.jsx);
- owners em `frontend/src/app`, `frontend/src/pages`, `frontend/src/features` e
  `frontend/src/shared`;
- renderizações condicionais e estados inline nos componentes;
- testes em `frontend/test`;
- [Design System](DESIGN_SYSTEM.md),
  [Visual Validation Log](validation/VISUAL_VALIDATION_LOG.md),
  [contratos da API](../api/API_CONTRACTS.md),
  [matriz de autorização](../security/AUTHORIZATION_MATRIX.md) e
  [matriz RF](../traceability/RF_TECHNICAL_MATRIX.md).

## Status taxonomy

| Visual Status    | Uso                                                                                                                          |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `C2 COMPLETE`    | A surface segue o TraceFlow Hybrid C2 em Light, Dark e composição responsiva, com evidência suficiente para a classificação. |
| `LEGACY`         | A surface ainda utiliza predominantemente a linguagem visual anterior.                                                       |
| `HYBRID`         | A surface combina shell, tokens ou primitives C2 com conteúdo ainda legado.                                                  |
| `NOT REVIEWED`   | A surface foi identificada, mas faltam evidências para classificar sua linguagem visual.                                     |
| `NOT APPLICABLE` | O item rastreado não possui apresentação visual própria.                                                                     |

Prioridade visual:

- `P0`: surface quebrada, ilegível ou inacessível para uso;
- `P1`: próxima fase de redesign;
- `P2`: dívida visual relevante, sem bloqueio imediato;
- `P3`: baixo impacto;
- `—`: baseline aprovada ou primitive transversal sem redesign pendente.

## Validation taxonomy

| Validation Status         | Uso                                                                                  |
| ------------------------- | ------------------------------------------------------------------------------------ |
| `VISUALLY APPROVED`       | Homologação renderizada concluída no escopo registrado no log versionado.            |
| `TECHNICALLY VERIFIED`    | Código e testes sustentam a evidência declarada, sem equivaler a homologação visual. |
| `STRUCTURALLY IDENTIFIED` | Rota, owner, trigger e estados foram localizados por auditoria estrutural.           |
| `ENVIRONMENT BLOCKED`     | A validação pretendida não pôde ser executada por limitação objetiva do ambiente.    |
| `NOT VALIDATED`           | A surface existe, mas ainda não possui validação registrada.                         |

As colunas Light, Dark, Responsive e Accessibility registram evidência separadamente. “Tokenizado”
não significa “homologado”, e teste estrutural não substitui inspeção renderizada.
`TECHNICALLY VERIFIED` limita-se ao comportamento explicitado nessas colunas e nas notas; não prova
todos os estados de uma surface. `ENVIRONMENT BLOCKED` não é aprovação nem falha. Uma mudança
material posterior preserva a entrada histórica no log, mas exige reconsiderar o status atual até a
revalidação.

## Global / Auxiliary Surfaces

O runtime atual não possui sistema de toast, notification center, popover, action sheet ou skeleton.
Feedbacks são inline; os overlays reais são o drawer do shell, `NewProjectDialog`, `ConfirmDialog` e
`TaskDetailsPanel`. Esses owners estão catalogados nos respectivos fluxos.

`ProjectJoinCard` exporta um wrapper sem consumer de produção; apenas `ProjectJoinForm` é usado pelo
dialog e o wrapper aparece em teste isolado. Classificação: `DEPRECATED / UNREACHABLE` para o wrapper,
sem remover código nesta auditoria.

## Legacy and Hybrid Summary

Não foi identificado P0 visual confirmado nesta auditoria. A evidência histórica de Auth e Account
Lifecycle está versionada; o Login atual aguarda revalidação após mudança material. Os principais
grupos P1 remanescentes são:

1. **Tasks:** a página de Tasks, formulário, lista e pickers permanecem legados; o Kanban e seus
   dialogs agora usam C2, mas aguardam homologação renderizada integrada.
2. **Requirements/Traceability:** navegação já vive no shell C2, e formulários, listas, matriz e
   canvas possuem compatibilidade Dark; o canvas preserva sua light island categórica. O redesign
   continua adiado.
3. **Repository:** filtros, summary e tabela possuem compatibilidade Dark, mas ainda pertencem à
   linguagem anterior.
4. **Project Audit:** a rota continua legada e sem entrada na navegação; Settings é C2 e possui
   validação granular própria, sem promover Project Audit por associação.

A compatibilidade de tema registrada não altera a classificação LEGACY/HYBRID nem antecipa o
respectivo UX scope de redesign.

## UX Scope Planning

Os identificadores `UX-*` organizam somente a evolução visual e sua validação. Eles não substituem
Sprints, RFs, cards do roadmap nem a linhagem técnica/histórica E0-E15 preservada em migrations,
scripts, ADRs, testes e documentos de refatoração.

### UX-FOUNDATION — Shell / Design System / Theme Foundation

- Design System e tokens semânticos;
- shell autenticado, sidebar, drawer, quick projects e primitives transversais;
- preferências Sistema/Claro/Escuro e resolução do tema;
- bypass block, landmarks e comportamento responsivo do shell.

### UX-PROJECTS — Projects / Overview / Edit / Members

- catálogo, Create/Join e feedback auxiliar;
- Project Overview e sincronização GitHub contextual;
- Edit Project;
- Members, convites, Access Code e confirmações relacionadas.

### UX-AUTH — Auth + Auxiliary Flows

As 15 surfaces de Auth e Account Lifecycle usam C2 Focused. A evidência renderizada histórica está
no log; o status corrente continua granular no inventário. Não criar página visual própria para
`ANONYMIZED`: o estado vigente não autentica. Callbacks iniciados dentro de Settings permanecem no
escopo UX-SETTINGS; as callbacks públicas de mudança de e-mail e reativação pertencem a UX-AUTH.

### UX-SETTINGS — Home + Settings + Auxiliary Surfaces

- Home/Entry: confirmar `/projects` como entrada autenticada C2 já aprovada, sem criar dashboard;
- Settings shell e navegação por links de rota C2;
- Account: profile, username, e-mail pendente, sensitive reauth e deactivate confirmation;
- Security: criar/alterar senha, reauth, sessões, empty e revoke confirmation;
- Privacy: export, deletion default/pending, request/cancel confirmations e feedback;
- Integrations: GitHub OAuth identity, callbacks, link/unlink e confirmation;
- Integrations: GitHub App empty/list, authorization callback e disconnect confirmation;
- states compartilhados de loading/error/feedback dentro de Settings.

### UX-TASKS-KANBAN — Tasks

- Tasks main, loading, fatal error e feedback;
- formulário create/edit e validações;
- lista, empty state e ações;
- pickers de requisito, PR, commit e issue;

- confirmação de exclusão;
- Comments panel, loading, empty, error e composer;
- comentários próprios, de terceiros, editados e menu de ações;
- composer edit mode e confirmação de exclusão;

- histórico automático, recovery de background e indicador de novos comentários;

### UX-PLANNING-KANBAN — Kanban

- header contextual sem retorno redundante, resumo transversal e seletor pesquisável/múltiplo de Sprint com URL compartilhável;
- filtros secundários recolhíveis, result count, clear e filtered empty;
- quadro responsivo com três status reais, colunas com scroll interno e scroll horizontal em containers estreitos;
- cards compactos sem overflow menu, com contexto explícito de Sprint no recorte global, details no corpo, histórico independente e supressão de click após drag;
- drag-and-drop, moving, conflito `409` e reconciliação sem reclassificar mutation confirmada;
- Task Details com leitura/edição unificada autorizada, status read-only, dirty combinado, reset por taskId e delete interno;
- rastreabilidade categorizada e rolável dentro da única ação Editar tarefa, com buscas latest-wins, mutations independentes e sucesso parcial honesto;
- sugestões de commits em controle compacto compartilhado com Tasks, tooltip acessível, single-flight e feedback sem estatísticas técnicas;
- ações externas do GitHub em anchors C2 com ícone semântico; Comments com altura estável, lista rolável e composer fixo;
- histórico individual por tarefa com filtros, paginação, loading, empty e erro;
- confirmação de exclusão, feedback e estados assíncronos;
- lacuna registrada: o DnD HTML nativo ainda não oferece movimento de status por teclado.

### UX-PLANNING-SPRINTS — Sprints

- título contextual enxuto, resumo operacional com cinco células reais sem filler e filtros recolhíveis com quantidade ativa e result count;
- grid responsivo, card Nova sprint e cards por status;
- dialogs de criação, edição, tarefas e evolução;
- pesquisa de Marcos e tarefas, menu de ações e confirmações;
- empty, filtered empty, loading, error e stale refresh warning.

### UX-PLANNING-MILESTONES — Marcos

- título contextual enxuto, resumo e filtros recolhíveis de status/prazo/Sprint com quantidade ativa;
- grid responsivo, card Novo marco e cards abertos, concluídos ou atrasados;
- prazo do Marco separado do progresso derivado das Sprints;
- dialogs de criação, edição e consulta de Sprints vinculadas;
- pesquisa acessível de Sprints, seleção múltipla, menu de ações e confirmação de exclusão;
- empty, filtered empty, loading, error e stale refresh warning;
- nenhum `startDate` de Marco e nenhum threshold de “Atenção” sem regra de domínio.

### UX-PLANNING-SCHEDULE — Cronograma

- resumo operacional Situação atual com Sprint atual, próximo Marco e somente deadlines próprios atrasados;
- calendário mensal com lanes de Sprint acima dos números, até três faixas, overflow, prazo de Marco e deadline de tarefa;
- dez cores semânticas automáticas com mapeamento determinístico, prevenção de colisões visíveis e continuidade entre meses;
- hoje e dia selecionado como estados independentes, com legenda por forma e texto;
- painel Contexto único com modos Mês/Dia por buttons com `aria-pressed`, troca automática ao selecionar data e body rolável;
- modo Dia separando eventos datados de contexto ativo da Sprint e do Marco relacionado;
- próximos prazos em grid responsivo, completo e rolável, limitado a deadline de tarefa, `dueDate` de Marco e fim de Sprint;
- navegação de mês derivada do dataset já carregado, sem request por célula, dia ou hover;
- nenhum início, fim ou intervalo artificial de Marco e nenhum threshold oculto de atenção;
- empty, filtered empty, loading, forbidden, error e composição responsiva por container.

### UX-REQUIREMENTS-TRACEABILITY — Requirements + Traceability

- Requirements main, loading, fatal error e feedback;

- busca/seleção de tarefas e no-results;

### UX-REPOSITORY-AUDIT — Repository / GitHub + Project Audit + Remaining Surfaces

- Repository: main, filtros, help, loading/error/empty e artifact table;
- Project Audit: main, empty e error;
- decidir a ausência de consumer frontend para account audit sem inventar uma surface.

### UX-FINAL-VALIDATION — Final Surface Validation

- revalidar shell e primitives compartilhadas;
- verificar Light/Dark e responsividade de todas as surfaces concluídas;
- executar keyboard/focus/return-focus nos dialogs e drawer;
- validar empty/loading/error/success/rate-limit sem confundir teste estrutural com homologação;
- atualizar `Visual Status` e `Validation Status` somente com evidência real.

## Audit Notes

- Todas as rotas declaradas em `AppRoutes.jsx` foram mapeadas, inclusive redirect de `/`, nested
  routes de Settings e wildcard 404.
- A auditoria cruzou arquivos, imports, JSX condicional e testes; não se limitou ao route table.
- `OWNER`, `MANAGER`, `MEMBER` e `VIEWER` são os únicos papéis de projeto usados. `OWNER` não é
  administrador do sistema.
- Usuário autenticado sem membership pode acessar a plataforma e `/projects`; recursos de projeto
  sem membership permanecem inacessíveis.
- GitHub OAuth foi catalogado como autenticação/identidade. GitHub App/Installation foi catalogada
  como integração de repositórios e artefatos.
- Surfaces de features planejadas, sem owner/runtime atual, não foram incluídas nos totais. O item
  `ACCOUNT-AUDIT-UNIMPLEMENTED` é mantido fora dos totais apenas para registrar a lacuna entre o
  endpoint documentado e o frontend atual.
- O log preserva a homologação histórica, enquanto este inventário registra o estado após mudanças
  materiais. Protótipos locais não promovem uma surface nem substituem evidência versionada.
